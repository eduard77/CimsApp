## Retrospective

### What went well

- **Triple Option A held cleanly.** Spec-and-defer for pen test,
  k6 OSS for load test, env-vars for secrets. 9-for-9 across S10
  through S19. The pattern is now the established muscle memory
  for sprint kickoffs.
- **The OWASP review found real issues.** Three concrete
  fix-forwards (A05 missing security headers / HSTS, A06
  vulnerable transitives, A07 no password complexity). The A05
  + A07 fixes landed in the same commit as the review; A06 is
  tracked because dependency upgrades risk cascade conflicts
  worth handling separately. Generalisable: a methodical
  per-category walkthrough beats a "let's hope we're secure"
  posture; the catch rate is high.
- **Splitting agent-doable from external-dependency work was
  honest.** PAFM F.18 specifies four bullets, two of which the
  agent fundamentally cannot execute (external tester + deployed
  load-test rig). Rather than pretend they're done or skip them,
  the sprint delivered the SPEC for each and named the
  external-execution gate explicitly. The user sees a clean
  hand-off to commission / run; no ambiguity about what's left.
- **k6 + JavaScript load testing has a great signal-to-effort
  ratio.** 100 lines of script encodes the 100-VU acceptance bar
  with inline thresholds. The exit-code-as-CI-gate pattern means
  the load test slots into any CI pipeline without bespoke
  reporting plumbing. No paid service, no cloud lock-in.
- **The OWASP A06 finding is the kind of thing that's only found
  by tooling, not code review.** Three high-severity transitive
  vulnerabilities I would never have spotted by reading service
  code. Generalisable: include `dotnet list package
  --vulnerable --include-transitive` in the standing pre-ship
  audit checklist.

### What did not go well

- **ADR numbering collision.** The kickoff doc said ADR-0015 for
  secrets management, but ADR-0015 was already taken (ci-runner-
  shape). Renumbered to ADR-0016 at write time. Cost: minutes
  of confusion + the s19.md sprint log carries an explicit note
  about the renumbering. Generalisable: at sprint kickoff,
  `ls docs/adr/ | tail -5` before naming the new ADR.
- **B-115 vulnerable-package upgrades NOT fix-forwarded.**
  The high-severity transitives are real exposure that v1.0
  shouldn't ship with. Tracked as B-115 with a "fast-follower
  in S19 if dependencies cooperate" disposition, but the work
  didn't land this sprint. Risk: deferred to v1.1 in fact even
  if "fast-follower" in name, unless someone commits the upgrade
  before S22 ship gate. The S22 retrospective should re-check
  this status.
- **No live verification.** The OWASP review fixes (security
  headers, HSTS, password rule) were reviewed statically but
  not exercised against a running instance in this session.
  WDAC blocking local tests AND the dev server requiring a
  process restart for the middleware change to take effect
  meant the verification step was deferred. The new test
  (`Register_with_too_short_password_throws_400`) covers the
  password rule via CI; the headers + HSTS are CI-pending.

### What surprised me

- **The OWASP review took less time than estimated** (~45 min
  rather than 4h). The codebase is mature enough that most
  categories landed at PASS with citations rather than analysis.
  The categories that surfaced findings (A05, A06, A07) were
  the ones I had concrete prior expectations about ("no security
  headers" was a known gap from prior glance at Program.cs);
  the rest were affirmation, not discovery. Generalisable: the
  review's value is highest on the categories where you DON'T
  have prior context; budget time for those, not for the
  obvious-PASS categories.
- **Pen test specs are mostly logistics.** Threat model and
  scope-out are ~30% of the doc; engagement timeline,
  acceptance bar, deliverables expected, known-not-shipped
  items are the other 70%. The technical content is small; the
  non-technical-but-essential content is what makes the doc
  commission-ready vs commission-blocked.
- **k6 in JavaScript is genuinely fun to write.** Better
  ergonomics than JMeter / Gatling for a small load test.
  Scenario isolation via `group()`, threshold-as-pass-criteria
  inline in `options`, native check() on response codes. Worth
  carrying as the default load-test toolchain for this codebase
  going forward.

### What I will try differently next sprint

- **Pre-flight ADR numbering at kickoff.** Avoid the
  numbering-collision rework by checking
  `ls docs/adr/ | tail -5` before the kickoff doc commits.
- **Schedule the B-115 upgrade explicitly.** Rather than letting
  it drift as a "fast-follower if dependencies cooperate," put
  it on the S20 calendar at the start of S20 kickoff (or earlier
  if the user wants it before S20). Vulnerable transitives are
  the kind of obligation that grows scarier the longer it sits.
- **Live-verify the security headers** at the start of the next
  session — restart the dev server, hit any endpoint, inspect
  the response headers in the browser's network panel. 30-second
  check, catches a configuration regression cheaply.

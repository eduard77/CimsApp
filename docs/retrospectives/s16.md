## Retrospective

### What went well

- **Triple Option A held cleanly through to close.** Scope (4
  pages), audit viewer (extend existing shape), routing/layout
  (flat /admin/* with no AdminLayout) — none re-litigated.
  Triple-Option-A pattern now empirically 6-for-6
  (S10 / S11 / S12 / S14 / S15 / S16).
- **Reuse over rewrite paid off.** The existing
  `AuthService.RevokeUserTokensAsync` /
  `DeactivateUserAsync` and `InvitationService.CreateAsync`
  cover three of the admin actions verbatim — only the new
  list / role-set / org-update / invitation-revoke / audit-list
  surfaces are new code. UserAdminService is ~140 LOC despite
  doing four things, because three of them are existing service
  calls re-exposed through a paging wrapper.
- **The pain that drove the sprint was concrete.** Within the
  same session as the kickoff, the operator (the user) had just
  walked through the laptop-pickup ritual: PowerShell to bootstrap
  an org, PowerShell to register, raw SQL `UPDATE Users SET
  GlobalRole = 0` to promote to SuperAdmin. Every step now has a
  UI surface. When the next operator hits this, it'll be one
  page, not three CLI commands.
- **Privilege-escalation guard caught at design time.** The
  `SetGlobalRoleAsync` method had three potential footguns
  (self-target, OrgAdmin-grants-SuperAdmin, cross-tenant
  targeting). Naming all three at design time before writing the
  body meant they each landed as an explicit guard with a
  matching test. Post-implementation discovery would have meant
  refactoring tests to add coverage; design-time naming kept
  the test file in lockstep.

### What did not go well

- **Windows Defender Application Control / Smart App Control
  blocked test execution.** First sprint where this has actually
  bitten. The earlier 930 / 930 pass in the same session ran
  against a previously-trusted `CimsApp.dll` hash; every
  rebuild produces a new hash that the policy re-evaluates.
  `Unblock-File` (zone-identifier) and full clean rebuild
  didn't help — the policy is hash-based at the kernel level.
  The build itself succeeds; only the xunit discoverer's
  reflection-load is blocked (error `0x800711C7`).
  Workarounds NOT yet tried (would need a separate session
  with admin context): add a WDAC rule for the project bin dirs,
  toggle Smart App Control off, sign the assemblies. Pragmatic
  resolution this session: commit the test file with an
  explicit verification-pending note in the commit body and
  defer verification to the desktop machine or CI.
- **The post-S1 handoff flagged this issue for `CimsApp.exe`
  but didn't enumerate the tests-specific case.** The
  `dotnet bin/Debug/net8.0/CimsApp.dll` workaround addresses
  the exe block (running the app); it does NOT address the
  xunit-loads-the-dll-via-reflection block. Worth carrying
  forward as a separate documented case in the laptop's
  environment notes.
- **No live test of the admin pages end-to-end through the
  browser before commit.** With WDAC blocking tests AND limited
  session scope, browser-side smoke walk of the four pages was
  deferred. The dev server is up at
  `https://localhost:55069` and the pages compile + route
  cleanly, but "render an empty list" vs "render an actual
  result set with the expected actions" wasn't manually verified
  for /admin/organisations or /admin/audit. The kickoff doc's
  Top-3 risk #2 (cross-tenant leak via paged list endpoints)
  has unit-test coverage; the *visual* confirmation of the
  shape is still owed.

### What surprised me

- **Just-in-time admin UI is actually small.** Four pages came
  in at ~100 LOC each. The reason: every action is a single API
  call, and the response shape (`AdminPagedResult<T>`) lets
  the same MudTable + paging-footer pattern apply to all four.
  The earlier guess was "this is a UI-heavy sprint that'll
  burn the buffer"; reality was the buffer was barely touched.
  Lesson: admin surfaces benefit disproportionately from the
  read-mostly + paged-list pattern.
- **The existing role-claim pipeline is enough.** No new
  client-side role-gating logic was needed for the nav; the
  `[Authorize(Roles="OrgAdmin,SuperAdmin")]` server-side gate
  + each page's "Insufficient permissions" empty state covers
  the UX without exposing GlobalRole to the client. Previous
  predictions for an admin-console sprint assumed a client-side
  role check would be needed; this turned out to be over-design.
- **WDAC is a real, recurring tax on per-machine dev.** First
  sprint where it actually blocked work flow. The next time a
  fresh machine joins the project, this'll show up again.
  Solving it once at the policy layer (WDAC rule for project
  bin dirs OR signed assemblies) would amortise across every
  future sprint on every machine.

### What I will try differently next sprint

- **Live-browser smoke of new UI pages before commit.** The
  pages compile, route, and have correct contracts, but seeing
  them with real data catches things unit tests don't (mud
  table column overflow, missing icons, page-empty states).
  The dev server is already running this session; it's a
  zero-cost discipline to add to T-SXX-04.
- **Surface WDAC blockers earlier.** The discovery-time error
  showed up at the test step. If the laptop's WDAC posture
  blocks reflection-load on every rebuild, we'll hit this on
  S17 too. Carrying as a session-start check: "can I rebuild
  + test-run a no-op change without WDAC firing?" — if not,
  resolve before committing new code.
- **Consider promoting the WDAC fix to a v1.1 backlog entry.**
  Not strictly project work, but real friction. If the desktop
  doesn't hit this and the laptop does, signing the assemblies
  (or carrying a WDAC supplemental policy) is a one-time
  resolution. Decided NOT to add it as B-NNN this sprint —
  it's developer-environment territory, not product backlog.
  Carrying as a known operational follow-up instead.

## Retrospective

### What went well

- **Triple Option A held cleanly.** Per-module markdown files
  (vs single manual), three admin docs, walkthrough scripts
  with video deferred. 11-for-11 across S10 → S21.
- **22 user-doc files at ~150-300 words each is a workable
  shape.** Tight enough to write quickly; long enough to be
  useful. The "what + who + key actions + common gotchas"
  template carried across all 22 with minor variations per
  module's specific flow.
- **Cross-references are the multiplier.** Every doc points
  at the relevant ADRs, PAFM appendices, role-matrix, prior
  sprint retros. The docs aren't standalone; they're a
  navigation layer over the existing project artefacts.
- **The walkthrough scripts double as test plans for v1.0
  acceptance.** Each script's "Expected" blocks are
  verifiable assertions against a deployed instance — a
  pilot operator running through the scripts is effectively
  doing acceptance testing.

### What did not go well

- **No live verification of the docs against the running app
  this session.** Build wasn't required (no code change), but
  it would have been good to dev-server up and validate that
  e.g. the screenshots-in-place markers are accurate. Carries
  forward as a v1.1 polish opportunity — running through the
  walkthrough scripts on a deployed staging instance is
  exactly the user-action-gate pattern S19's pen test
  follows.
- **Some module docs lean on the existing test / sprint-log
  content rather than new prose.** That's efficient but means
  if the underlying content rots, the user docs rot with it.
  Mitigation for v1.1: a docs-CI check that validates
  cross-references resolve.
- **No screenshots.** The walkthrough scripts have
  "Screenshot here:" markers but I couldn't capture screenshots.
  v1.1 / B-124 (training videos) will provide the visual
  reference; until then the scripts are prose-only.

### What surprised me

- **22 modules is a real catalogue.** Each one is a small
  surface but writing a useful doc per module forced me to
  re-read the kickoff + retro for that sprint to remember
  what shipped vs what was deferred. The retros + sprint logs
  are the source of truth for "what does this module actually
  do at v1.0" — re-affirming the value of writing them as the
  sprint closes.
- **Admin docs are the most operationally useful.** The
  `troubleshooting.md` in particular maps real failure modes
  (CI smoke flake, OrgUpdate 404 by design, etc.) to
  remediations. That's the kind of doc the operator opens
  during an incident — and it cost ~30 min to write.
- **Swagger UI being dev-only is a real limitation for v1.0
  pilot.** External auditors (B-109 / S18) and integration
  teams can't browse the API surface from production without
  a temporary `ASPNETCORE_ENVIRONMENT=Development` flip. v1.1
  candidate: env-var-controlled Swagger-in-prod toggle (not
  yet a B-NNN; raise if pilot requests).

### What I will try differently next sprint

- **Live-verify each walkthrough script** before sprint close
  next time a docs-shape sprint lands. The scripts compile
  (markdown is correct) but their "Expected" blocks haven't
  been run end-to-end. Trivial to do; high value.
- **Add a docs / link-check** to CI. Cross-references that go
  stale are the predictable docs-rot mode. A simple
  `markdown-link-check` GitHub Action would catch ADR moves,
  PR-number drift, file renames.

## Retrospective

### What went well

- **Triple Option A held cleanly through to close.** Scope
  (responsive sweep, no PWA / offline / mobile-only paradigm),
  table strategy (CSS utility class column hiding, no per-page
  card-view rewrites), drawer breakpoint (Responsive variant at
  Sm) — none re-litigated. Pattern now empirically 7-for-7
  (S10 / S11 / S12 / S14 / S15 / S16 / S17).
- **CSS utility classes beat per-cell MudHidden wrapping.** The
  `d-none d-{breakpoint}-table-cell` pattern handles per-column
  hiding with one attribute per cell, no DOM tree changes, no
  per-page state. Easier to reason about than MudHidden wrapping
  and matches the rest of the MudBlazor utility-class ecosystem.
- **Form sweep audit found one real bug.** The
  AdminOrganisations Edit dialog overflow on mobile was a latent
  S16 oversight (added without DialogOptions; would have rendered
  at MudBlazor's default fixed dialog width). The audit was a
  zero-cost grep; the fix was one attribute. Generalisable: every
  new dialog should land with `Options='new DialogOptions{...
  FullWidth=true}'` even if MaxWidth defaults to a sensible value.
- **The sprint stayed light.** 13h estimate, all five
  pre-T-S17-06 tasks landed in roughly that envelope. The risk
  flagged in the kickoff ("the sweep is broader than estimated")
  did not materialise — only six MudTable pages turned out to
  exist, not the predicted ~10. The grep-driven discovery
  (`grep -l MudTable CimsApp/Components/Pages/`) caught the actual
  scope in one command.

### What did not go well

- **Manual viewport verification (T-S17-05) was deferred.** This
  is the second sprint in a row where browser-side visual
  verification couldn't happen inside the same session as the
  commits. S16 retro flagged it as "what I will try differently";
  S17 hit the same wall because the agent cannot drive a browser.
  The sprint shipped honestly (T-S17-05 explicitly marked deferred
  in the sprint log) but the gap is real — a UI sprint without
  visual verification is structurally incomplete. Carrying as a
  permanent constraint of the dev environment, not a sprint
  failure.
- **No tests added means no regression net.** UI sprints don't
  get behavioural test coverage in the established pattern (no
  service / contract surface to test). If a future change breaks
  the responsive layout, only manual visual verification will
  catch it. Could imagine a Playwright-class E2E test suite that
  emulates mobile viewports and asserts on rendered DOM, but
  that's a separate sprint and a new tooling commitment — flag
  for v1.1.

### What surprised me

- **MudBlazor's CSS utility classes are well-curated.** The
  `d-none d-sm-table-cell` / `d-md-table-cell` pattern is exactly
  what's needed for per-column responsive hiding. Discovered
  during the kickoff via the existing inline-style grep; no
  searching, no docs hunting beyond confirming the breakpoint
  names. Worth carrying forward as the default pattern for any
  future per-element responsive logic in this codebase.
- **`Variant.Responsive` on MudDrawer just works.** The kickoff
  Risk #2 ("desktop regression while making mobile work") didn't
  materialise — the responsive variant honours initial
  `Open=true` as "expanded persistent" above the breakpoint and
  ignores it as "ready-to-show but currently hidden" below.
  Single component, single attribute change, byte-identical
  desktop.
- **The `Documents.razor` table was the only non-admin page that
  needed touching.** Most other pages (Actions, Rfis, Projects,
  Templates, Dashboard) use card-list / grid layouts that already
  reflow naturally because `<MudGrid Spacing="2">` with
  `<MudItem xs="12" md="6" xl="4">` is responsive by construction.
  The mobile-pain was concentrated in the table-rendering pages,
  not the rich-card pages.

### What I will try differently next sprint

- **Surface T-S17-05 user-action gate explicitly at kickoff.**
  The kickoff doc said "manual viewport sweep" but didn't make
  it explicit that this step requires the user, not the agent.
  Future UI sprints should mark such steps `[USER]` in the task
  list so the gating is obvious upfront and the sprint plan
  doesn't *imply* the agent will do them.
- **Consider a Playwright-class E2E suite** for v1.1 — flag as
  B-105 if I add it, otherwise leave the gap acknowledged. The
  existing CI smoke tests (B-027 SQL Server smoke) cover real
  HTTP request shapes; a browser smoke would cover real DOM
  shapes. Mostly relevant if the codebase grows more
  responsive-style work.
- **Pre-empt the dialog-options miss at write time.** The
  AdminOrganisations dialog was a real bug fixed in T-S17-04;
  preventing the next instance is "every new MudDialog ships with
  DialogOptions" — promotable to a code-shape note rather than
  re-discovering each sprint.

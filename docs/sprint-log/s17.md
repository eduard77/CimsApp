## Module DoD (predicted, pending .docx reconciliation)

- Every existing page renders cleanly on a phone-narrow viewport
  (~375px width, single-column where appropriate)
- Sidebar nav adapts: persistent mini-drawer on desktop, slide-in
  temporary drawer with overlay on mobile
- Tables degrade gracefully: non-essential columns hidden under
  `sm` breakpoint, overflow scroll for the rest
- Form inputs remain touch-usable (MudBlazor defaults already do
  this; verify, don't redesign)
- No regressions on desktop layouts at `md`/`lg`/`xl` breakpoints

## Decisions required at kickoff

Three triple-decision Option A defaults — pattern carried from
S10 / S11 / S12 / S14 / S15 / S16 (6-for-6 so far).

### Decision 1 — Scope of v1.0 Mobile

- **Option A (default, lean):** **Responsive sweep across every
  existing page.** Sidebar drawer adapts. Tables hide non-essential
  columns under `sm` and use horizontal scroll for the rest. Forms
  inherit MudBlazor's touch-friendly defaults — verify, don't
  redesign. No new mobile-only pages, no different navigation
  paradigm, no PWA wrapper, no offline mode.
- Option B: Mobile-first UX redesign. Card-list views replace
  tables on mobile, bottom nav replaces sidebar, PWA shell, offline
  cache. ~3× the work, ships a parallel UX rather than adapting the
  existing one.
- **Choice:** **Option A.** B-102 unblock condition: "first pilot
  user reports the responsive table view as actively painful on
  their day-to-day mobile flow OR there's a concrete site-supervisor
  use case where offline read-of-last-known-state is the v1.0 ask".

### Decision 2 — Table responsive strategy

- **Option A (default, lean):** **MudTable horizontal scroll +
  per-column `Hidden` / `MudHidden` gating under the `sm`
  breakpoint.** Mobile sees the 3-4 most important columns; the
  rest drop under `sm`. Horizontal scroll handles overflow when a
  user actually needs to see hidden columns. Zero per-page
  rewrites; one-line column gating per non-essential `<MudTh>` /
  `<MudTd>` pair.
- Option B: Conditional component rendering — `<MudTable>` for
  desktop, card-list rendering for mobile via per-page `if
  Breakpoint.IsSmallerThan(Sm) { ...cards... } else { ...table... }`.
  Better mobile UX but doubles the per-page surface and tests.
- **Choice:** **Option A.** B-103 unblock condition: "pilot user
  reports table-on-mobile as the primary friction point AND the
  hidden-columns approach hides data they need to see frequently".

### Decision 3 — Sidebar drawer breakpoint behaviour

- **Option A (default, lean):** **`MudDrawer Variant="Responsive"`
  with breakpoint at `sm`.** Above breakpoint: persistent mini
  drawer (current behaviour). At/below breakpoint: temporary
  slide-in drawer with overlay, opened by a hamburger toggle in the
  top bar (new component). One drawer component, per-breakpoint
  behaviour, MudBlazor handles the transition.
- Option B: Bottom navigation bar on mobile, sidebar on desktop.
  Adds a new component, requires per-page consideration, and
  diverges from the desktop mental model.
- **Choice:** **Option A.** Bottom-nav alternative → v1.1 / B-104
  unblock condition: "pilot user reports sidebar-on-mobile as
  worse UX than expected from a mobile-app-style alternative".

## Top-3 risks (CATEGORY only — S9-retro pattern)

1. **Inline-style proliferation gets worse, not better.** Existing
   pages use a lot of inline `style="..."` declarations with fixed
   pixel widths / paddings. The temptation in a responsive sweep is
   to add `@media`-shaped logic into inline styles, which is hard
   to reason about and harder to test. Mitigation: prefer
   `<MudHidden>` and Mud component breakpoint props over inline
   `@media` queries; fixed pixels stay only where MudBlazor
   defaults already use them (avatar sizes, icon sizes).
2. **Desktop regression while making mobile work.** Adding
   responsive logic can change desktop layout if not careful with
   breakpoint defaults. Mitigation: every change must be verified
   at desktop-default viewport (≥ `md`) before commit; the
   acceptance bar is "mobile works AND desktop is byte-identical".
3. **The sweep is broader than estimated.** Hidden-column gating
   touches ~10 pages × ~5 columns each = ~50 attribute additions.
   Easy to miss a page. Mitigation: grep-driven discovery —
   `grep -l "MudTable" CimsApp/Components/Pages/` lists every page
   that needs the sweep; check each off in T-S17-03.

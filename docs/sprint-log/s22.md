## Decisions required at kickoff

Three triple-decision Option A defaults — pattern carried from
S10..S21 (11-for-11 so far).

### Decision 1 — UAT scope and gating

- **Option A (default, lean):** **2-week UAT with one
  internal test user against one representative pilot
  project.** Test user follows the three training walkthrough
  scripts (`docs/training/*.md`) end-to-end + free-form
  exploration of the surfaces relevant to their actual
  role. Defects logged as GitHub issues tagged
  `uat`. Critical-severity (data loss, auth bypass,
  cross-tenant leak, app unrecoverable) blocks ship; High
  severity gets a written mitigation; Medium/Low triage to
  v1.1.
- Option B: Multi-user UAT with two pilot tenants
  concurrently. Better signal but harder to coordinate;
  v1.1 / pilot-2 territory.
- **Choice: Option A.**

### Decision 2 — Release versioning + tagging

- **Option A (default, lean):** **Annotated git tag `v1.0`
  on the release-candidate commit** (after all blocking UAT
  findings + the pen test + load test pass). Tag message
  references the PAFM compliance status, the OWASP review
  sign-off, and the carry-forward closures. Subsequent v1.1
  work tags as `v1.1-*` when each sprint closes.
- Option B: Semantic versioning with patches (v1.0.0,
  v1.0.1, etc.). Premature for the v1.0 internal pilot
  scope; revisit when the release cadence demands it.
- **Choice: Option A.**

### Decision 3 — CHANGELOG shape

- **Option A (default, lean):** **Single `CHANGELOG.md` at
  repo root** following the Keep-a-Changelog convention
  (Added / Changed / Deprecated / Removed / Fixed / Security).
  v1.0 entry summarises the 22 PAFM Appendix F modules
  shipped + the post-S1 hardening retired + the security
  posture (OWASP signed off, zero vulnerable packages).
- Option B: Per-sprint CHANGELOG entries auto-generated from
  retros. Lower-effort but loses the high-level v1.0
  framing the pilot-onboarding context wants.
- **Choice: Option A.**

## Task decomposition

| Task | Description | Hours (agent / user) |
|---|---|---|
| T-S22-01 | Sprint kickoff: branch + this doc | 1 / 0 |
| T-S22-02 | CHANGELOG.md drafting | 2 / 0.5 (review) |
| T-S22-03 | Go-live checklist | 1.5 / 0.5 (review) |
| T-S22-04 | UAT execution + fix-forwards | 0–10 / 10–20 |
| T-S22-05 | Pen test close-out | 0–8 / external + 1 (commission) |
| T-S22-06 | Load test close-out | 0 / 1 (run) |
| T-S22-07 | Release candidate tag + deploy | 0.5 / 1 |
| T-S22-08 | Sprint close + v1.0 retro | 1 / 0 |
| **Total agent** | (excluding UAT fix-forward variance) | **6h** |
| **Total user** | (UAT + external commissions + run) | **15-25h** |

The agent's 6h is the **deterministic** work — kickoff, release
artefacts, retro. UAT fix-forwards are open-ended (depend on
findings) and the user's UAT execution is calendar-bound (2
weeks at low intensity, not 10h continuous).

**This sprint cannot single-session compress.** It can sprint-
compress **the agent's deterministic part** in a session +
defer the user-driven gates to their own calendar.

## Top-3 risks

1. **Critical UAT finding lands late.** A Critical-severity
   finding two days before planned ship would push the date.
   Mitigation: structured walkthrough scripts + the agent's
   fix-forward capacity make defect→fix→re-test cycles fast.
2. **Pen test report identifies a Critical.** The OWASP review
   was internal; the external pen test may surface novel
   findings. Mitigation: the spec doc names the v1.0
   acceptance bar (zero open Critical, mitigation plan for
   any High); written commitment to that bar at commission
   time.
3. **Load test fails the p95 < 1s threshold.** Per S15 retro,
   search at >1000 rows is the most likely culprit. Mitigation:
   B-095 (FTS upgrade) is pre-flagged; trigger if load test
   exposes the issue.

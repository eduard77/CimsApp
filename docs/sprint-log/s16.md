## Pain that drives this sprint

The user just walked through the laptop-pickup ritual:
PowerShell `POST /api/v1/organisations` → capture bootstrap token →
PowerShell `POST /api/v1/auth/register` → SQL `UPDATE Users SET
GlobalRole = 0` to promote to SuperAdmin. Every step has API plumbing
but no UI. Every prior sprint retro that mentions an admin task
ends with "via SQL" or "via the standing post-S0 SQL UPDATE". This
sprint closes the UI gap.

## Module DoD (predicted, pending .docx reconciliation)

- User administration (list users in tenant, deactivate, revoke
  tokens, mint invitations) — UI surface
- Organisation administration (edit Name / Code / Country,
  deactivate; SuperAdmin sees all orgs, OrgAdmin sees own)
- Invitation management (mint, list active, revoke pending)
- Tenant-scoped audit log viewer (cross-project for the operator's
  org; SuperAdmin sees all tenants)

## Decisions required at kickoff

Three triple-decision Option A defaults — pattern carried from
S10 / S11 / S12 / S14 / S15.

### Decision 1 — Scope of v1.0 Admin Console

- **Option A (default, lean):** **Four pages.** `/admin/users`
  (list users in tenant, deactivate, revoke tokens, set
  GlobalRole), `/admin/organisations` (SuperAdmin-only org
  management; OrgAdmin sees own org settings page), `/admin/invitations`
  (mint, list active, revoke pending), `/admin/audit` (tenant-scoped
  audit viewer with date / action / entity filters). Reuses
  existing `AuditLog` schema, existing `AuthService` revocation
  primitive, existing `InvitationService.CreateAsync`. No new
  entities; one new admin-list service per surface.
- Option B: Comprehensive admin including system health, feature
  flags, perf metrics, queue depths, log rollups. Sprint-and-a-half
  scope; v1.0 pilot doesn't need most of it.
- **Choice:** **Option A.** B-099 unblock condition: "first pilot
  operator request for cross-tenant impersonation, system health
  view, or feature-flag toggle".

### Decision 2 — Org-wide audit log viewer

- **Option A (default, lean):** **Extend the existing `Audit.razor`
  shape from project-scoped to tenant-scoped at `/admin/audit`.**
  Direct EF query against `AuditLogs` with paging (50 / page) +
  filters (date range, action contains, entity equals, user
  equals). Acceptable on pilot scale (low-thousands of rows).
  Index/projection optimization → v1.1 / B-100 if pilot scale
  exposes latency.
- Option B: Materialized AuditView projection table for performance
  + dedicated indexes for the common filter shapes. Premature for
  v1.0 pilot scale.
- **Choice:** **Option A.** B-100 unblock condition: "audit-page
  load exceeds 1s on a tenant with > 10000 audit rows".

### Decision 3 — Routing, layout, and role gating

- **Option A (default, lean):** **Per-page MudBlazor pages under
  `/admin/*` with a top-level `[Authorize(Roles="OrgAdmin,SuperAdmin")]`
  gate via the existing role-claim pipeline.** No shared
  AdminLayout.razor wrapping component — each page is independent
  and uses the same `<PageHeader>` shape as the existing pages
  (Audit.razor / Projects.razor / Documents.razor pattern). Side
  navigation gets four new entries gated by role-claim presence.
  SuperAdmin sees all four pages including org list across
  tenants; OrgAdmin sees three pages scoped to own tenant
  (no cross-tenant org list — ADR-0007 boundary preserved).
- Option B: Dedicated AdminLayout.razor with sidebar nav, breadcrumbs,
  separate `/admin` shell. More polish, more invasive, doesn't
  match the rest of the app's flat-page convention.
- **Choice:** **Option A.** No B-NNN — Option B is a UX-polish
  fast-follower, not a structurally-different decision.

## Top-3 risks (CATEGORY only — S9-retro pattern)

1. **Privilege escalation via role-set endpoint.** The "set
   GlobalRole" admin action (`/admin/users/{id}/global-role`)
   could let a malicious OrgAdmin promote themselves or another
   user to SuperAdmin if the gate is wrong. Mitigation: only
   SuperAdmin can set `GlobalRole = SuperAdmin`; OrgAdmin can
   only set `OrgAdmin` / `null` within their own tenant.
   Per-action authorisation test exercises every (caller-role ×
   target-role × tenant-match) cell.
2. **Cross-tenant leak via paged list endpoints.** Each admin
   list endpoint must honour the existing query filter (tenant
   scoping via `ITenantContext`). Mitigation: every list service
   query goes through standard `db.<DbSet>` (carries global
   filter); per-service tenant-isolation test confirms an admin
   in Tenant A cannot enumerate Tenant B's users / invitations /
   audit rows. SuperAdmin path uses `IgnoreQueryFilters` per
   ADR-0007 — covered by separate "SuperAdmin sees all" test.
3. **Audit log viewer information disclosure.** Tenant-scoped
   audit rows include `Before` / `After` JSON which can carry
   sensitive entity state. Mitigation: query filter restricts
   rows by `User.OrganisationId` (existing
   `AuditLogUserIdNullable` semantics from PR #41 — anonymous-actor
   rows are hidden from tenant queries). The
   `AuditInterceptor.SkippedFieldNames` already excludes
   PasswordHash / TokenHash from `Before` / `After` JSON
   (PR #42 era). One test confirms the listing endpoint
   honours the existing filter; one test confirms the response
   shape includes no fields that bypass `[JsonIgnore]`.

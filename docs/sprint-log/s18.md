## Decisions required at kickoff

Three triple-decision Option A defaults — pattern carried from
S10 / S11 / S12 / S14 / S15 / S16 / S17 (7-for-7 so far).

### Decision 1 — Evidence library shape

- **Option A (default, lean):** **Discriminated-link entity.**
  `EvidenceArtefact (Id, ProjectId, ComplianceAreaId, AddedById,
  AddedAt, DocumentId? RfiId? AuditLogId? InspectionActivityId?
  Description?)` with exactly one of the nullable FK fields set
  per row. ComplianceArea is an enum on the entity (UkGdpr /
  Bsa2022 / Iso19650 / Nec4 / QualityHse / Other; v1.0 starting
  set). Query joins to the existing entity for body content;
  evidence row is metadata-only. Per-tenant via Project's
  AppointingPartyId filter.
- Option B: Duplicated body — copy the relevant entity's fields
  into the evidence row at attach time. Survives source mutation
  but doubles storage and breaks audit chain ("did the evidence
  capture match the source as of attach date?" — answerable, but
  needs a separate version pin).
- **Choice:** **Option A.** Source-of-truth stays single; the
  audit-twin atomicity (PR #33) means the source entity's history
  is already captured by AuditLog rows. If a source row is later
  modified, the evidence still references it; export can show
  the as-of-export-date snapshot of the source plus the
  AuditLog trail.

### Decision 2 — External Auditor role scope

- **Option A (default, lean):** **Project-scoped invitation
  + new `UserRole.ExternalAuditor` enum value.** External
  auditor registers via a normal Invitation (single-use,
  project-bound, expiring), gets the ExternalAuditor role on a
  new `AuditorProjectAssignment (UserId, ProjectId, ScopeAreas,
  ExpiresAt)` row, and the standard tenant query filter restricts
  them to the assigned project. ScopeAreas is a flag enum (which
  ComplianceAreas they're allowed to see). On expiry: aggressive
  TokenInvalidationCutoff bump + cascading deny via the standard
  cutoff/refresh-sweep machinery (ADR-0014). Read-only — the
  ExternalAuditor role is rejected by every controller's
  mutation gate.
- Option B: True cross-tenant scoping — auditor's User row
  lives in their own tenant (their auditing firm), and they see
  the auditee's tenant via a per-User `VisibilityGrant` table.
  More aligned with how external auditors actually work but
  adds a substantially more complex query-filter override path.
- **Choice:** **Option A.** B-109 unblock condition: "first pilot
  external audit where the auditor's home tenancy / firm needs
  separate accounting from their per-engagement access".

### Decision 3 — Audit export format

- **Option A (default, lean):** **ZIP bundle.** Each evidence
  row exports as a per-row JSON/MD record + a manifest at the
  bundle root listing all rows + a copy of the AuditLog trail
  scoped to the export window. Reuses existing JSON serialization
  (no PDF rendering dep). External auditor downloads the .zip,
  unpacks, reviews. Trivial to inspect with any text editor or
  diff tool.
- Option B: Single multi-section PDF. Prettier, single artefact
  to email/archive, but adds a PDF rendering library dependency
  (Ch 24.6 24-hour wait for new lib) + per-section layout work.
- **Choice:** **Option A.** B-110 unblock condition: "external
  auditor or pilot stakeholder explicitly requests a PDF
  artefact for audit-archive ergonomics".

## v1.1 candidates pre-flagged

- **B-109 — External Auditor cross-tenant scoping.** Auditor's
  User row in their own (auditing firm) tenant; per-User
  VisibilityGrant table grants access to specific projects in
  other tenants. Aligns with how external auditors actually
  operate (a single auditor across multiple client engagements).
  Unblock: first pilot engagement where the auditor's home
  tenancy / firm needs separate accounting from their
  per-engagement access.
- **B-110 — PDF audit export format.** Single multi-section
  PDF with cover page / table of contents / per-evidence
  formatted sections. Adds a PDF rendering library (Ch 24.6
  24-hour wait). Unblock: external auditor or pilot stakeholder
  explicitly requests PDF artefact ergonomics over ZIP.
- **B-111 — Per-tenant evidence-library template / required-set.**
  Tenant defines "evidence required for each compliance area"
  (e.g. UK GDPR requires DPIA + RoPA + breach-process artefacts);
  evidence library shows percentage-complete per area. Unblock:
  pilot operator requests guided / checklist-style evidence
  collection.

## Top-3 risks (CATEGORY only — S9-retro pattern)

1. **External Auditor query-filter correctness.** The ExternalAuditor
   tenant-filter override has to: (a) restrict the auditor to
   their assigned project, (b) hide other projects in the same
   tenant from view, (c) deny access to mutation endpoints, (d)
   flip to deny on assignment expiry. Each is a separate test
   case; missing any one is a real privilege-escalation bug.
   Mitigation: per-rule test, plus a "honeypot project" pattern
   in the tenant-isolation tests where the ExternalAuditor in
   project A tries to GET / POST against a project B in the same
   tenant — must 404 / 403.
2. **Evidence row referential leak.** A discriminated-link
   evidence row references one of Document / RFI / AuditLog /
   InspectionActivity. If the source row is later deleted or
   reassigned, the evidence row becomes stale. Mitigation: soft
   constraint at service-layer (evidence add validates the
   target exists AND is in the same project); hard constraint
   at FK level so source-side delete cascades or is blocked.
   v1.0 chooses block (no source-side delete is currently
   implemented for these entities — the codebase is
   audit-trail-friendly by default).
3. **Audit export surface area.** The export builder reads
   from many entities (evidence + AuditLog + the per-evidence
   source rows). Each query can hit hot data. Mitigation:
   bounded by date range (required input); paged internally
   per entity type so a runaway export doesn't OOM. Stream the
   ZIP rather than building in memory.
